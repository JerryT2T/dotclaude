≈ 4 min

Gemeinsamer Engpass ist #1100: Solange niemand bestätigt, dass die Mod im Desktop Code-Tab überhaupt lädt, sind alle Desktop-Aussagen der anderen Issues ungeprüft. Ein unbeaufsichtigter Run kann Code und Tests liefern, aber keinen Desktop-Lauf.

Jede Empfehlung trennt deshalb: was der Run allein bauen kann, und was einmal deine Hand am Desktop braucht.

Gilt für: #1100 · docs/dev/mods.md

Upstream-Bug anthropics/claude-code#105936 ist offen: im Desktop Code-Tab bleibt eine Mod nach „Turn them on“ ungeladen. Ob das auf deinem Build (Engine 2.1.321, Windows) auch passiert, weiß niemand.

Wer klärt, ob die devops-Mod im Desktop lädt?

Ein objektives Signal existiert schon: ~/.claude/devops-mods-loaded.json.

session.start der Mod schreibt diese Datei, und ss.mods.load.js meldet beim nächsten Start, wenn eine Session keinen Eintrag hatte. Der Lauf ist damit: Mod-Feature auf alpha, Desktop-Session öffnen, „Turn them on“, Datei prüfen, Pane sichtbar?

Ein „Workaround bestätigt“ ohne diesen Lauf wäre ein falscher Beleg in der Dev-Doku.

Gilt für: #1101 · hooks/mods

Spike 1 hat 17 passive Zeilen: Pausen bis 59 min lesen 97–99,9 % aus dem Cache, ab 60 min nur noch 9–54 %. Ein $.model.fork-Ping wurde nie gemessen.

Was gilt als Beleg, bevor der Keepalive gebaut wird?

Das passt zu einer 1-h-TTL, beweist aber nicht, dass ein Fork bei ~55 min den Eintrag verlängert. five_hour ist in jeder Zeile null, die 5-h-Delta-Regel ist also auch ungeprüft.

Gilt für: #1103 · hooks/mods, concept-watch

Ob $.clock + $.prompt.submit eine untätige Session weckt, zeigt nur eine Live-Session. Die Engine-Tests prüfen nur Aufruf-Formen.

Wie geht es mit den Concept-Timern weiter?

Unbeaufsichtigt prüfbar ist nur die Idempotenz der Timer, nicht das Wecken.

Die Probe würde einen Timer setzen, nach Ablauf einen Marker-Prompt senden und protokollieren: gefeuert, gesendet, Turn gestartet, Session untätig oder beschäftigt. Ein grüner Stub-Test darf nie als Beleg für das Wecken gelten.

Offen bleibt außerdem ein Handshake, damit Mod-Timer und Watcher nie beide wecken (Red-Team-Befund 3 in mods.md).

Drei Issues brauchen eine Richtung von dir, bevor der Run baut.

#1102 (Titel aus der Mod), #1105 (Recap bei Rückkehr) und #1106 (große Pastes auslagern) sind keine reinen Spikes: hier fehlt eine Produktentscheidung. Bei #1106 hat der Run die Engine-API inzwischen geprüft.

Gilt für: #1102 · prompt.flow.title-work, lib/session-title

Die Mod-API hat keine dokumentierte Umbenennen-Funktion. Ob ein Mod-Rename den custom-title-Eintrag schreibt, den drei Leser brauchen, zeigt nur Spike 3 am Desktop.

Wie wird #1102 geschnitten?

Einziger bekannter Schreiber ist heute das App-Tool set_session_title.

Es hängt einen custom-title-Eintrag an, gespiegelt als agent-name (lib/session-title.js). Eine Mod kann dieses Tool nicht aufrufen. Ein verdrahteter Stand-down-Marker könnte eine Session ganz ohne Titel-Schreiber lassen; Teil A verdrahtet deshalb nichts.

Gilt für: #1105 · hooks/mods

Die Mod-API kennt kein Fokus- oder Leerlauf-Ereignis, nur session.start, turn.start und prompt.submit. Bei turn.start hast du schon getippt.

Wann gilt eine Session als „zurückgekehrt“?

Der warme Pfad ist dünn belegt: genau eine passive Messung (59 min, 98,3 %).

Für den kalten Pfad fehlt Material: das Atom lastCard hält nur {title, at}, die volle Card wird beim nächsten Prompt gelöscht. Ein neuer State-Key muss in types/index.d.ts stehen, sonst lehnt claude plugin validate ihn ab.

Gilt für: #1106 · hooks/mods, paste-redirect, pre.tokens.guard

Geklärt: prompt.submit kann den Text per next({...e, text}) ersetzen, tool.call kann nach await next(e) das Ergebnis ersetzen. Offen ist nur die Prüfung im Desktop.

Was baut der nächste Run für #1106?

Ausnahmen stehen schon in der Lib: /do-run-, AUTOSTART- und <command-name>-Prompts bleiben unverändert, weil ss.run.task und prompt.run.contract den Text lesen. Risiko: ein Auszug kann den fehlschlagenden Test verstecken (Red-Team-Befund 7); das Original bleibt deshalb immer als Datei lesbar.
